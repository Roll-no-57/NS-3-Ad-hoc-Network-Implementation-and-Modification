1. Introduction: The Scenario

Real-Life Application: The project focuses on a disaster response scenario where a natural disaster has destroyed the existing ground infrastructure.


Proposed Solution: To establish communication, a swarm of Unmanned Aerial Vehicles (UAVs) is deployed to create a Flying Ad-Hoc Network (FANET).


Primary Goal: The network must relay live video footage from the search area back to a remote Base Station.


The Constraint: Standard routing protocols, such as AODV, blindly select the shortest path for data transmission. This approach ignores drone speed and drains the battery life of specific "central" nodes, leading to frequent link ruptures and ultimately, mission failure.
+1

2. Problem Statement
The primary flaw in standard AODV routing is that it utilizes Hop Count as its only metric.


Flawed Decision Making: Standard AODV would decide that a 3-hop path moving away at 50 m/s is superior to a 4-hop path where drones are hovering efficiently.


Consequences: * Critical nodes experience energy depletion and die prematurely.

Fast-moving nodes cause route instability by breaking links immediately.

The network experiences high packet loss when it is forced to constantly reconstruct routes.

3. Project Roadmap: Core vs. Extension
This project proposes a robust implementation based on the fitness function methodology introduced by Taha et al., which is then extended with mobility awareness to better suit FANET environments.

Phase 1: The Core Target (Reproduction)


Fitness Function AODV (FF-AODV): The goal is to replace the traditional "Shortest Path" logic with a multi-metric "Fitness Function".


Logic: A score (F) is calculated by combining Residual Energy and Distance metrics.


Status: This serves as the base implementation derived from Taha et al..

Phase 2: Custom Modification (Mobility-Aware)


Velocity-Aware Optimization: The baseline methodology by Taha et al. does not account for the speed of the nodes.


Solution: The fitness function will be extended to penalize nodes moving at high velocities.

Integration Logic:


Step 1: A Route Request (RREQ) arrives at a given node.


Step 2: The node compares its own current speed against the Maximum Speed.


Step 3: A Stability Score is calculated, where faster nodes receive lower scores.


Step 4: The routing table is updated only if the newly proposed path provides the optimal balance of Energy, Distance, AND Stability.

6. Implementation Details (ns-3)
The project requires modifying the C++ source code located in src/aodv.


Step 1: Energy & Mobility Awareness 

Install the BasicEnergySource onto the nodes.

Access MobilityModel::GetVelocity() to retrieve real-time speed data.


Step 2: Modify Route Request (RREQ) 


File: aodv-packet.h.

Add the fields m_pathFitness and m_velocity directly to the header.

Intermediate nodes must update these fields as the RREQ travels through the network.


Step 3: Decision Logic 


File: aodv-routing-protocol.cc.

Within RecvRequest(): Retrieve the velocity norm, calculate the new fitness utilizing Energy, Hops, and velocity, and update the route if the new fitness exceeds the stored fitness.

7. Evaluation Strategy
The simulation will compare Standard AODV against FF-AODV using three key performance metrics:


Network Lifetime: This measures the time elapsed until the very first node dies. The hypothesis is that FF-AODV will significantly outlast Standard AODV because it balances the network load.
+1


Packet Delivery Ratio: This tracks the percentage of successful video packets delivered. The goal is to maintain high reliability by actively avoiding fast-moving, unstable nodes.
+1


Average Throughput: This measures the rate of successful data delivery over the communication channel in Kbps.
+1

9. Expected Outcomes

Outcome 1: Successfully achieving a working "Fitness Function" integrated inside the ns-3 AODV module (Phase 1).


Outcome 2: Generating validated results that demonstrate increased Network Lifetime and effective load balancing, where traffic actively moves away from nodes with low batteries.


Outcome 3 (Custom Mod): Proving an improved Packet Delivery Ratio in scenarios with high-mobility (20-50 m/s) by successfully avoiding unstable and high-velocity nodes.
